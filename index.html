GenAI / RAG

Kubernetes Gated RAG

A Kubernetes Q&A system that answers only from the docs you ingest, with a gate at every stage that could let a bad answer through.

0.95faithfulness on the 8-row starter set
3generation failover links, same model
2cache layers, exact and semantic

Overview

Most RAG demos stop at retrieve and generate. This one treats every step as a place where something can go wrong. A question passes an input safety gate and a topic gate before any generation call is spent, retrieval must clear a hard rerank threshold or the system reports no grounded docs, and the generated answer is safety-checked again before it is shown or cached.

How it works

  • Two cache layers, exact match then semantic similarity, sit in front of retrieval. Keys include schema, policy, and corpus versions, and each ingest fingerprints the docs collection, so re-ingesting or changing a policy invalidates stale answers automatically.
  • Follow-ups are rewritten into standalone questions first. If the rewrite differs from the raw message and misses the exact cache, it gets its own safety check, and an unusable rewrite marks the turn degraded so no cache is read or written.
  • Generation fails over across Groq, a second Groq account, and NVIDIA NIM, all on the same model. The point is separate rate-limit budgets, not model diversity, and each link fails over immediately on timeouts, rate limits, 5xx and auth errors, and empty or truncated completions.
  • Ingestion sends every file through an LLM relevance gate and uses deterministic point IDs, so edits replace rather than duplicate. A noisy_data folder exists to prove the gate rejects off-topic content.

Guardrails

  • Known jailbreak patterns block locally for free. Everything else goes to NeMoGuard and then the planner chain, and a classifier outage returns a temporarily unavailable response instead of a pass.
  • Input safety, response safety, topic gating, and every provider link each run behind their own circuit breaker: open after consecutive failures, admit one probe after the recovery window, reopen if it fails.
  • Rerank is fail closed. Only chunks that reach the 0.5 rerank threshold go to the generator, and the prompt restricts the model to the supplied context.
  • A Qdrant, embedding, reranker, generation, or classifier failure is never cached and never reported as a policy refusal, so an outage cannot harden into a wrong cached answer.

Results

  • On the 8-row starter set, generation scored faithfulness 0.95, answer relevancy 0.91, context precision 1.00, context recall 0.94, context entity recall 0.90, and semantic similarity 0.91.
  • Generation is gpt-oss-120b on Groq and the judge is gemini-3.5-flash, a different model family. Read this as proof that the harness runs end to end, not as a benchmark.

Limits

  • Each eval row brings its own hand-written contexts, so the metrics do not score the retriever, gates, or caches, and faithfulness is easier than on real retrieval. Eight rows cannot support strong conclusions, there is no ablation harness, and guardrails are verified only by unit tests.
  • Ingested chunks go straight into the generation prompt with no injection filtering, and the local jailbreak patterns are English-only regexes. Caches are local to one host, and removing a source document requires a full wipe.

AI Agents

Competitive Intelligence Agent

An autonomous research agent that turns a company name into a sourced intelligence brief, and marks anything it cannot source as unknown.

+1.0completeness gain from the Critic loop (0 to 5, n=5)
+0.8groundedness gain from the Critic loop (0 to 5, n=5)
3max replan cycles

Overview

Given a company or product name, the agent plans research sub-questions across five required fields (what it does, funding and ownership, recent news, competitors, risks), runs web search and calculation tools, and writes a brief where every claim carries a numbered citation. It critiques its own coverage and can send itself back to re-plan. A paired ablation on its own Critic loop measures what that loop buys and what it costs.

How it works

  • Each role runs on a model matched to a free-tier quota by call volume: Nemotron 3 Super on NIM plans, gpt-oss-120b on Groq executes at up to 8 steps per plan, Gemini 3.5 Flash-Lite critiques, and Gemini 3.5 Flash writes the one call the reader sees. The Critic and Synthesizer use different models so they draw from separate quotas.
  • The Critic checks coverage against the five fields and can loop back to the Planner up to 3 times, each replan targeting only flagged gaps. With the Critic disabled the node is absent from the graph entirely rather than skipped, which keeps the ablation clean.
  • Postgres memory is keyed by a normalized entity name and tracks each field's age. Fields under 7 days old seed the run, except recent news, which is always re-researched. A fuzzy match scoring 90 or more only raises a warning, so Meta is never silently confused with Meta Financial Group.

Guardrails

  • Hard stops at 3 replans, 15 tool calls, 8 steps per plan, and 8 minutes. On any limit the run returns what it confirmed and marks the rest insufficient information. Duplicate queries skip the tool call and reuse the cached result.
  • Search results are wrapped in untrusted-content delimiters with embedded tags neutralized, as a prompt-injection mitigation. Field statuses are checked against the scratchpad, so a field cannot be reported as confirmed without evidence behind it.
  • Every LLM call has a 60 second timeout and bounded retries. If the Critic fails the run goes to synthesis, and if the Synthesizer fails a plain report is built from the scratchpad with no LLM at all and is never cached.
  • The pytest suite runs fully offline with every LLM, Tavily, and Postgres call stubbed, and a consistency test checks that README links and code references in the architecture doc resolve.

Results

  • On 5 hand-picked companies (Anthropic, Stripe, Notion, Figma, Databricks), an isolated Groq judge scored groundedness 4.6 with the Critic against 3.8 without, and completeness 4.8 against 3.8.
  • The price was about 10.8 tool calls against 6.2 and roughly 96 seconds against 40, at an average of 1.6 replans. The Critic improved both scores at about 1.7x the tool calls and 2.4x the time.

Limits

  • n=5 is a smoke test. One noisy judge call can move an average by 0.2, so the full 15-company benchmark is the number to trust. Free-tier quotas make that run hard: it needs 30 Synthesizer calls against roughly 20 requests per day on the Synthesizer model.
  • Search returns snippets with no credibility filtering, so a cited source can be weak: citations prove provenance, not reliability. Whether the prose matches its citation numbers is judged by the model, not verified in code.
  • The wall clock is checked between steps, so a run can overrun by one in-flight call. The API has no rate limiting and the Streamlit UI has no authentication.

AI Agents / MCP

IssueOps MCP

A GitHub issue triage server where the model can only propose. Nothing reaches GitHub until a human approves it.

10MCP tools: 5 read, 5 propose
0execute tools exposed to the model
48hproposal expiry window

Overview

An MCP client such as Claude, or a triage agent, can read issues and propose comments, labels, assignments, and closes. Ten tools sit on the model-facing surface: five read-only, and five that only queue a proposal in Postgres. No execute or confirm tool exists on that surface. A person reviews each proposal in a Streamlit dashboard, and every read, proposal, and decision lands in an audit log.

How it works

  • The GitHub write token lives in exactly one process, the dashboard, in its own env file. The loader never reads it from a file for any other process, drops it if inherited, and hides credentials from the config repr.
  • Approval claims the row atomically under a lease token that every later write requires, so concurrent approvals cannot double execute and no database lock is held across GitHub calls. The issue is then re-fetched, and the row becomes stale if the title or body changed, a close target is no longer open, or an identical comment already exists.
  • The triage agent uses the same propose path. It classifies open issues with gpt-oss-20b on Groq, one call per issue, and is limited to labels and assignments unless comments and closes are explicitly enabled and the issue is unflagged.

Guardrails

  • Proposals are validated before queuing: repo allowlist, arguments, pull requests rejected, per-issue (10) and per-initiator (500) caps under advisory locks, and dedup of identical pending proposals, all audited.
  • A network error or 5xx mid-write is recorded as needs_review, never guessed or auto-retried. Approvals stuck for 10 minutes return to the queue if GitHub was never called, or are held for review if it may have been. Unapproved proposals expire after 48 hours.
  • Issue text is untrusted: prompt markers are stripped so an issue cannot forge a closing tag, and a heuristic injection flag gives the approver an advisory hint. It is not a security boundary, because the real control is that every proposal is scoped to one issue and needs human approval.
  • The GitHub client has a 15 second timeout, pagination raises instead of truncating, and next-page links must point to api.github.com.

Results

  • On a 12-issue fixture, 9 legitimate and 3 adversarial, against gpt-oss-20b: label accuracy 9 of 9, no injected marker echoed in model output (0 of 3), and about 4.2 seconds average model latency per issue.
  • All 3 adversarial issues still produced a planned proposal, so proposal-level susceptibility reads 3 of 3. That can mean correct spam triage or obedience and the metric cannot tell them apart, but a human approval stands between every proposal and GitHub either way.
  • The harness also cross-checks the audit log against the proposal table in both directions, which catches bookkeeping bugs in this codebase, not writes made elsewhere. CI runs integration tests against Postgres 16 on Python 3.10 and 3.12, covering concurrent approvals, lease reclamation, and deadlock freedom.

Limits

  • Approver identity is a typed name, not authentication. The access token gates the app but does not distinguish approvers.
  • All processes share one Postgres role, so the audit log is append-only by convention, not by database permission. The fixture is n=12, a smoke test and not a security or accuracy benchmark.
  • Expiry runs only when the dashboard loads, so an unattended queue can block new proposals through its caps. No scheduler is included, and issue text is sent to Groq and stored in Neon.

MLOps

Continuous Credit Risk Governance Pipeline

A credit-risk model that runs its own lifecycle: it scores, watches for drift, retrains, gates its own promotions, and rolls itself back.

1%false retrains on undrifted batches (was about 40%)
3promotion checks: tolerance, dominance, significance
105automated tests

Overview

A model does not stay good because it was good at launch. This pipeline simulates life after deployment on the Give Me Some Credit dataset: a recession scenario is injected into 318 live batches of 200 rows, and the pipeline has to notice, challenge the champion, and replace it with no human in the loop. Each clock tick runs in one database transaction, and a GitHub Actions cron advances the clock every 3 hours.

How it works

  • A challenger is promoted only if it passes three ordered checks: it is not worse than the champion by more than 0.01 AUC-PR, it beats the champion outright, and a 2,000-resample bootstrap CI on the matched-batch AUC-PR delta clears zero. Significance decides, and McNemar is logged as a diagnostic only.
  • Drift uses a per-feature K-S test forced on every feature, and a 3-batch cooldown stops persistent drift from retraining on every tick. The challenger trains on 3,000 base rows plus up to 6,000 recent labeled rows and is gated on a labeled batch it never saw.
  • A 0.03 AUC-PR drop against the stored reference only screens for rollback. The decision is a paired bootstrap of the previous champion against the current one on the same live batch, suppressed when the reference has gone stale, measured by which features drifted and not by raw p-values.

Guardrails

  • Labels are released only after a 3-batch delay, the true label is never stored beside model inputs, the stream is carved out before the base pool, retrains exclude the gate batch, and imputation medians come from the base pool only.
  • Postgres decides the champion. MLflow alias moves cannot join the transaction, so they happen last, and every tick starts by resetting @production to the database champion. Ticks are claimed with FOR UPDATE SKIP LOCKED, and a failed tick rolls back and retries cleanly.
  • K-S is pinned because Evidently switches to Wasserstein above 1,000 reference rows and misses heavy tails such as DebtRatio. Every decision, including rejections and skipped rollback checks, goes to the audit log.

Results

  • Raising the drift-share threshold from 0.1 to 0.3 cut false retrain triggers on undrifted batches from about 40% to about 1%. A threshold of 3 or more of 10 features flagging by chance at K-S alpha 0.05 is rare, which is why 0.3 holds.
  • The 25-tick demo covers persistent drift from batch 10 and temporary concept drift in batches 15 to 19. It took about 90 seconds against local Postgres and a local MLflow store.
  • The 105 tests include end-to-end checks that gate-batch rows never leak into training, the cooldown holds, aliases reconcile, and a failed tick rolls back cleanly. Integration tests run against Postgres 16 in CI.

Limits

  • About 200 rows and 13 positives per batch widen the confidence interval, so real improvements are often rejected, rollback rarely has an earlier champion, and McNemar rarely reaches 15 discordant pairs.
  • Drift is measured on the current batch but labels belong to an earlier one, so trigger and gate can sit in different regimes. K-S detection power on 200 rows is unmeasured.
  • The model is a deliberately plain logistic regression because the loop around it is the deliverable. A tick's transaction spans MLflow calls, and models are stored as pickles, which is safe only with a trusted remote.

Causal Inference

Causal Impact & Heterogeneous Response Analysis

Tests four causal estimators against a full-data reference effect before trusting any of them on a real segment-level question.

+417%naive OLS bias at strong confounding
0.0565Qini coefficient, 95% CI 0.030 to 0.085
1.12critical Gamma, fragile to hidden bias

Overview

The Criteo Uplift dataset holds 13,979,592 rows from a randomized ad experiment. Even there, the raw difference in means (0.01034) overstates the covariate-adjusted reference effect (0.00715, 95% CI 0.00689 to 0.00740) by 45%, so the benchmark is a cross-fitted AIPW estimate on all rows. A subsample is then confounded on purpose to see whether naive OLS, matching, IPW, and AIPW recover that reference as confounding gets worse. Only after that does the project ask which audiences responded, and whether the answer holds up.

How it works

  • Confounding is induced by a retention rule on the covariate most correlated with the outcome (f9), calibrated until a gate confirms the naive estimate misses the reference, then repeated over 20 independent 300,000-row replicates so estimator bias is separated from sampling noise.
  • A minimum-detectable-effect calculation at the real arm sizes chose visit over conversion. The visit effect is 1.8 times its MDE (relative MDE 10.4%), while the conversion effect sits right at its MDE (relative 51.2%), too coarse for per-segment estimates.
  • A calibrated T-learner scores individual effects on clean randomized data and is judged against random targeting with a bootstrapped Qini coefficient. Users are then clustered with KMeans and each segment gets a cross-fitted AIPW effect, checked with Benjamini-Hochberg correction, a Cochran Q heterogeneity test, and per-segment power.

Guardrails

  • All estimators share one cross-fitted propensity (5 folds, clipped to 0.001 to 0.999) and one trimmed population, naive OLS included. AIPW outcome models are cross-fitted too, and matching is true 1:1 without replacement with a 0.2 logit SD caliper.
  • Rosenbaum bounds on the matched pairs report how much hidden confounding would overturn the result. A critical Gamma below 1.5 is classed fragile.
  • The single LLM step critiques balance and overlap diagnostics, falls back from Groq to NVIDIA NIM to a rule-based critique, and never touches an estimate or a p-value. Data loading validates row count, columns, and base rates and fails loudly on drift.

Results

  • Naive OLS bias against the reference grew from +44% with no confounding to +417% at strong severity. At that severity PSM sat 43% below the reference, IPW 47% above, and AIPW 36% below.
  • IPW and AIPW stayed within 8% through mild confounding, but no estimator recovers the reference at strong severity, and IPW and AIPW drift in opposite directions for a cause that is not yet isolated. Matching cut the largest standardized difference from 0.387 to 0.023 across 23,294 pairs (18.4% of treated).
  • The T-learner's Qini coefficient is 0.0565 (95% CI 0.0301 to 0.0854), better than random targeting. Segment effects differ (Cochran Q 26.9, p = 6e-06, I-squared 89%), and two of four segments stay significant after correction: a 4.8% segment at 0.0368 (BH p = 5e-05) and the 39.4% segment at 0.0065 (BH p = 0.023). A 4.1% segment is inconclusive with only 932 control units.
  • Of 23,294 matched pairs, 714 are discordant and the critical Gamma is 1.12, so a hidden confounder shifting treatment odds by about 12% would overturn the matched result. That speaks to whether an effect exists, not its size. The Groq critique found no residual imbalance after matching and flagged the result as sensitive to hidden bias.

Limits

  • The reference rests on ignorability given 12 covariates. AIPW (0.00715) and IPW (0.00780) differ by more than the reference interval, so the true adjusted effect is only pinned to about 0.0071 to 0.0078.
  • Bias curves are specific to the covariate, retention rule, and replicate count, and the band is subsampling variability, not a confidence interval. PSM without replacement is capped by the retained control count.
  • Segment inference is approximate: Cochran Q is a large-sample approximation, adjustment covers only the 12 covariates, per-segment power uses one base rate for every segment, and the Qini interval is unadjusted. Rosenbaum bounds are PSM-only and one-sided.
  • Tests cover estimators, matching, Gamma, overlap, power, reference-effect estimation, and adjusted segment effects. Notebook logic, the data loader, the T-learner, and the dashboard are untested.

Experimentation

Experiment Design & Power Analysis for a Shipping Policy Change

A preregistered A/B pipeline in which the metric, minimum detectable effect, sample size, and tests are locked before any experimental data exists.

2,503sellers per arm required
2.0ppcomplaint-rate guardrail margin, frozen up front
71automated tests

Overview

Calibrated from the public Olist e-commerce dataset but simulated end to end. The question is whether free shipping raises average order value without raising complaint rates. The design, including a 2.0 percentage point non-inferiority margin on complaints, was committed before any simulation code existed. A population with a known injected effect (BRL 28.00 AOV, +1.2pp complaints) is then randomized and exactly the preregistered tests run once.

How it works

  • Sellers, not orders, are the randomization unit, since a seller's orders are not independent. Both potential outcomes are simulated, one is revealed per seller, and the counterfactual columns are dropped before analysis.
  • The primary test is a two-sided Welch t-test on seller AOV with a BRL 25 minimum lift. The complaint guardrail is a one-sided, margin-shifted z-test with seller-clustered standard errors, so it tests non-inferiority against the margin itself and returns passed, breached, or inconclusive.
  • A GO needs a significant, positive lift of at least BRL 25 and a passed guardrail, so a revenue win cannot mask a satisfaction loss.

Design integrity

  • analyze() takes its sample size from the frozen constants and raises PartialDatasetError unless each arm has exactly 2,503 sellers, which rules out peeking and stopping when p drops below 0.05. Odd seller counts and a seller appearing in both arms are rejected.
  • power_analysis raises DesignDriftError and writes nothing if the recomputed sample size differs from the frozen one, and a second analysis on different data raises ReanalysisError instead of overwriting.
  • AST tests verify that raw Olist data and the injected effect can never reach analysis or reporting code, and that the counterfactual cannot leak into the analysis data. The guards catch accidental drift, not tampering, and git history is the real lock.

Results

  • The verdict is NO-GO because the guardrail is inconclusive, not breached. Mean seller AOV rose from BRL 134.02 to BRL 172.09 (p = 8.6e-06), clearing the BRL 25 minimum. Complaints rose from 12.18% to 13.90%, a 1.73pp gap under the 2.0pp margin, but the margin-shifted test (z = -0.98, one-sided p = 0.163) did not establish non-inferiority.
  • Both injected effects were recovered against the realized values: AOV lift BRL 38.07 (95% CI 21.32 to 54.82) against BRL 30.84, and complaint difference +1.73pp (95% CI 1.18 to 2.27) against +1.35pp.
  • This reflects limited precision, not harm. The post hoc, unpreregistered power is roughly 89% at a true 1.2pp gap and 75% at the realized 1.35pp. The result is reported as it came out because the decision rule was fixed first.

Limits

  • Guardrail sizing is approximate: the 142 sellers-equivalent per arm comes from a pooled, order-level calculation that ignores within-seller correlation and answers a different question from the test that runs.
  • Recovery is a smoke test, since a correct 95% interval still misses about one run in twenty, and one seeded run does not show the method generalizes. Review score 2 or below is a proxy that is not specific to delivery.
  • The simulation matches only seller-level AOV spread and category mix to calibration. Multi-seller orders are credited whole to one seller, and baselines reflect Olist's category mix and the Brazilian market.

Customer Churn Prediction with Profit Optimization

Predicts churn, then decides whom to target by expected profit instead of a raw probability cutoff.

1.07Mraw transaction records
12RFM features per window
70offline unit tests

Overview

Predicts 90-day churn from a customer's transaction history on the Online Retail II dataset, calibrates the score into a real probability, and flags INTERVENE only when expected profit clears the offer cost: probability of churn times success rate times three months of spend, minus cost. A high-risk, low-spend customer can correctly be left alone. XGBoost is tuned and calibrated on separate validation data and the final test period is used once.

How it works

  • Sliding 365-day observation windows with a 90-day prediction horizon and a 30-day slide let one customer contribute several labeled examples across time. Twelve features per window cover recency, frequency, monetary, spend trend, purchase intervals, and a seasonal drop-off flag.
  • Validation is split by customer ID parity into a tuning half (Optuna, 50 trials, early stopping) and a calibration half (isotonic calibration and threshold selection on cross-fitted probabilities), so no role sees another's data.
  • A SHAP waterfall explains each single-customer prediction in the dashboard. It never touches training, tuning, or thresholding.

Leakage controls

  • The split is chronological with a 90-day embargo at each boundary, because labels look 90 days ahead and windows slide every 30. Ordering, disjointness, and the gap are asserted in tests, and the embargo purges 17,329 rows (40.3%) of the data.
  • A test inspects every fit call to enforce that the final model trains on the train split only, so validation stays genuinely held out. Credits are dated at the credit note, so a later return cannot change a window's features.
  • Cancellations stay as negative revenue at their own date and never count as a purchase when labeling churn, and the December 2010 sheet overlap is removed.

Results

  • On the final temporal test, PR-AUC on raw scores was 0.7452 and the Brier score on calibrated probabilities was 0.2073. Read PR-AUC against the base churn rate and Brier against a constant forecast, p times (1 - p).
  • Net campaign profit on the test set, under an assumed offer cost and success rate: £4,433 for random 20% targeting, £9,648 for a 0.5 cutoff, £16,817 for the profit-optimized global threshold, and £23,618 for the per-customer expected-value rule.
  • The locked threshold is 0.01, so the global policy is close to blanket targeting. Its edge over the 0.5 cutoff comes mainly from contacting more people, and the expected-value rule's lead is partly by construction.

Limits

  • Only about 10 windows exist, so after the embargo roughly 4 go to train and 1 each to validation and test. Threshold and profit figures rest on one period with no confidence interval, and no contact-everyone baseline is reported.
  • Customers recur across splits and windows overlap, so metrics are likely optimistic against a customer-disjoint test. The success rate is a configured constant where production would use an A/B test, and cold-start customers cannot be scored.
  • The 70 tests run on synthetic fixtures. They check code and leakage controls, not model quality.

DemandLens: Retail Demand Forecasting and Anomaly Benchmark

Retail demand forecasting and anomaly detection benchmarked across four models, with an LLM report whose every number is checked against source data.

60retail series benchmarked
0.974best holdout MASE, LightGBM, within 0.04 of two rivals
52automated tests

Overview

Benchmarks Prophet, SARIMA, LightGBM, and XGBoost on 60 retail series with a 15-day holdout, adds control-limit and Isolation Forest anomaly detectors, and generates an LLM narrative report. Heavy computation runs in Kaggle's free notebooks while a light local Streamlit dashboard reads only the saved outputs, so no number on screen comes from a different source than the notebooks produced.

How it works

  • ML features use lags of at least 21 days, and rolling statistics and oil price are shifted by the forecast horizon, so no feature sees in-window actuals. The final model is selected on mean MASE over 4 cross-validation folds, not on the holdout.
  • Every numeric claim in the LLM report is regex-checked against source facts before display, with provider fallback across Groq, NVIDIA NIM, and Gemini. Reports are saved to Supabase and downloadable as Markdown.
  • Metrics live in one module and are synced into the two notebooks that cannot import it, with a test that fails if the copies drift. Other tests parse the notebooks with ast to check that config values match notebook constants.

Guardrails

  • Anomaly evaluation injects 50 spikes and drops into 900 holdout rows, so scores are measured against known ground truth. Control limits are centered on each series' clean mean residual, so a constant forecast bias is not flagged.
  • Cost-of-error figures, about $224,480 for XGBoost against $225,702 for LightGBM, are labeled illustrative and use assumed grocery margins, not a real P&L.

Results

  • No model wins clearly. On the 15-day holdout across 60 series, LightGBM scored MASE 0.974, Prophet 0.996, and XGBoost 1.011, all within 0.04 of each other, and no significance test is included. SARIMA covers only 3 series, and on those like-for-like the MASE ranking is Prophet 0.793, SARIMA 0.838, LightGBM 0.919, XGBoost 0.933.
  • Control limits scored precision 0.824, recall 0.84, and F1 0.832. Isolation Forest scored precision 0.527, recall 0.96, and F1 0.681: it caught 48 of 50 but flagged about 43 clean rows, since 5% contamination flags about 5% of clean data by construction.
  • XGBoost was selected on cross-validation (0.866 against 0.902 for LightGBM) even though LightGBM scores slightly better on the holdout, and the choice is reported as made, not retrofitted.

Limits

  • This is backtesting on a 15-day holdout with known actuals, not live forecasting, and promotion and holiday flags are assumed known at forecast time. SARIMA ran on 3 series to save CPU, so its average is not like for like.
  • The grounding check is regex-based. It misses paraphrases with no literal number and can ground a wrong figure against an unrelated correct one, and reports with no numeric claims show as unverifiable.
  • Anomaly scores measure how detectable injected anomalies are, not performance on real incidents.

ReelBench: Multi-Stage Recommender Benchmark

Five recommendation approaches scored head to head on MovieLens 25M through one leakage-tested evaluation harness.

0.0485Recall@10 for SASRec + ranker, against 0.0243 for popularity
5approaches compared
0external calls at request time

Overview

A two-stage recommender, candidate retrieval followed by ranking, trained on free-tier GPUs and served entirely on CPU. The comparison table is the deliverable, not the model count or the UI. The harness was built and unit-tested before any model existed, so popularity, item-item CF, ALS, a two-tower retriever, and SASRec are all scored by the same code on the same held-out split of 12.45M implicit interactions.

How it works

  • A single global timestamp cutoff splits train and test. A per-user-only split can look correct for every user while leaking future signal across users, and a unit test built so the per-user check passes and the global one fails proves the difference.
  • Two-tower and SASRec embeddings feed a FAISS index, seen items are excluded, and a LightGBM LambdaRank model re-scores the survivors on similarity, recency, popularity, user activity, and genre match. Ranker labels come from a second temporal split inside train, so the test set is never touched.
  • Cold-start items get a separate FAISS index built offline from title and genre embeddings, because those spaces cannot merge with the learned ones. Serving never calls a model: FastAPI and Streamlit read cached artifacts only.

Guardrails

  • assert_no_leakage() hard-fails on train rows at or after the cutoff, test rows before it, or test users absent from train.
  • Item-item CF computes similarity in row-blocks with a bounded top-K per item, because a dense matrix over the 31,195-item catalog would be about 3.9GB at float32. A script measures its peak memory at that scale.
  • Both neural models checkpoint every epoch and resume, since free-tier GPU sessions can disconnect mid-training. Diagnostic and re-export scripts handle non-finite embeddings, and the FAISS index refuses to build from them.

Results

  • SASRec + ranker leads every accuracy metric: Recall@10 0.0485, NDCG@10 0.0432, and Recall@20 0.0832. ALS is the strongest single-stage model at Recall@10 0.0376, and popularity sets the floor at 0.0243.
  • Two-Tower + ranker lands at 0.0329, between popularity and ALS and level with item-item CF (0.0336), but has the highest catalog coverage at 5.4%. Coverage is under 6% for every approach, and diversity falls slightly as accuracy rises.

Limits

  • The neural rows are end-to-end pipelines (retrieval, filtering, re-ranking) and the baselines are single-stage models, so this is pipeline against single stage, not embedding against embedding. The ranker also uses item popularity as a feature.
  • One temporal split of 49,533 interactions, one run per model, and no confidence intervals, so third-decimal differences are not a ranking. ALS trains multithreaded and can shift slightly between runs.
  • MovieLens 25M is a static snapshot, and the two-tower uses no content features, so it generalizes to unseen users and items no better than ALS.
