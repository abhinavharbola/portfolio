GenAI / RAG

Kubernetes Gated RAG

A production-oriented RAG system for Kubernetes Q&A that answers only from ingested docs, defended in depth.

6Ragas metrics
3provider failover links
8starter eval rows

Overview

Every question passes a safety gate and a topic gate before a generation call is spent, then hard relevance thresholds on retrieval. The generated answer is safety-checked again before it is shown or cached.

How it works

  • Two cache layers, exact then semantic, are version-filtered so a policy or corpus change invalidates stale answers automatically.
  • Generation fails over across Groq, a secondary Groq account, then NVIDIA NIM on the same model, to draw on separate rate-limit budgets.
  • Infrastructure failures surface as temporarily unavailable and are never cached, so an outage cannot become a wrong cached answer.

Guardrails

  • Fail-closed safety: known jailbreak patterns are blocked locally, the rest go through NeMoGuard with a timeout and circuit breaker, and no usable verdict means block.
  • Only rerank-approved chunks reach generation. A reranker crash counts as an infrastructure failure, never a silent pass-through.
  • Rewritten, history-dependent questions are rechecked for jailbreak patterns before any cache lookup.

Evaluation

Ragas scores faithfulness, answer relevancy, context precision and recall, context entity recall, and semantic similarity. The judge is Gemini, a different model family from anything in the live pipeline. Scores are not published here yet.

Limits

  • The eval set is an 8-row starter set, not a benchmark. It tests grounding on supplied context, while the gates, caching, retrieval, and reranking are covered by unit tests instead.
  • No ablation compares the pipeline with a guardrail or cache layer switched off.

AI Agents

Competitive Intelligence Agent

An autonomous research agent that turns a company name into a sourced, traceable intelligence brief.

15companies in the eval benchmark
5required brief fields
3max replan cycles

Overview

Given a company or product name, the agent plans sub-questions, runs web search and calculation tools, and writes a brief with numbered citations. Anything it cannot source is marked insufficient information, never invented.

How it works

  • Planner, Executor, Critic, and Synthesizer each run on a different model, matched to that role's call volume and free-tier rate limits.
  • The Critic checks coverage against the five required fields and can send the run back to re-plan up to three times.
  • Postgres memory seeds a run from an exact entity match under 7 days old. Fuzzy matches are only flagged, never auto-seeded, to avoid conflating similar names.

Guardrails

  • Hard stops at 3 replans, 15 tool calls, and 8 minutes. On any limit the run returns what it confirmed and marks the rest insufficient information.
  • Search results are wrapped in untrusted-content delimiters before reaching any prompt, as a prompt-injection mitigation.
  • A failed Executor step blocks only that step. If the Synthesizer fails, a plain report is built from the scratchpad without an LLM.

Evaluation

A harness scores groundedness and completeness with an isolated judge model across 15 companies, then reruns the benchmark with the Critic loop off to measure what that loop adds. Ablation scores are not published here yet.

Limits

  • At small sample sizes, judge variance dominates the measured Critic effect.
  • The Executor's free-tier Groq quota caps it at roughly 60 to 70 full runs a day.

AI Agents / MCP

IssueOps MCP

A guarded MCP server for GitHub issue triage. Every mutating action is only proposed, and runs only after a human approves it.

10model-facing tools
0execute tools exposed to the model
48hproposal expiry window

Overview

Ten tools sit on the model-facing surface: five read-only, five that only queue a proposed comment, label change, assignment, or close for a human to review. No execute or confirm tool exists on that surface, for any client.

How it works

  • The GitHub write credential lives in exactly one process, the human-facing approval dashboard, and is dropped from every other process's environment.
  • Before executing an approved action, the dashboard re-fetches the issue and compares it to the snapshot taken at proposal time, marking the action stale on a mismatch.
  • Every read, proposal, approval, rejection, and execution writes to an audit log, so the log shows what happened on GitHub, not only what was attempted.

Guardrails

  • Identical pending proposals are deduplicated, and proposals older than 48 hours expire instead of running against a stale issue.
  • A heuristic prompt-injection flag appears in the dashboard as an advisory signal only. It is never in the approval path and is not a security boundary.

Evaluation

The harness measures how often the agent proposes a malicious action on adversarial issues (expected to be non-zero), runs a SQL check that every completed GitHub mutation has an approved proposal behind it (required to be zero), and reports label accuracy. It has not yet been run against live Neon or the real GitHub API, so no results are reported.

Limits

  • The approver identity is a free-text name, not authentication.
  • Interoperability with Claude Desktop has not been tested yet.

MLOps

Continuous Credit Risk Governance Pipeline

A self-governing credit-risk pipeline that scores, monitors drift, retrains, gates promotion, and rolls back on its own.

1%false retrains on undrifted batches (was 40%)
3promotion gates
54automated tests

Overview

Simulates what a portfolio usually skips: life after deployment. Each cycle scores a batch, releases delayed labels, checks drift, and if needed retrains a challenger and gates it against the champion. The data is cut into 637 batches of 200 rows, and a demo run advances 25.

How it works

  • A challenger is promoted only if it stays within a 0.01 tolerance band, beats the champion, and passes McNemar or a bootstrap interval when discordant pairs are few.
  • Rollback is held to the same rigor: a drop of 0.03 AUC-PR must be confirmed by a bootstrap interval, not a single noisy batch.
  • Every decision is written to an audit log, including rejections and suppressed rollbacks, not only actions that changed something.

Guardrails

  • Optimistic concurrency claims a batch before any work starts, so overlapping scheduled and manual runs cannot create duplicate predictions.
  • Labels are released only after a 3-batch delay, and the true label is never stored with model input features.
  • Imputation medians are fit after the split, after an earlier version leaked holdout information into training.

Results

  • Raising the drift-share threshold from 0.1 to 0.3 cut false retrain triggers from about 40% to about 1% of undrifted batches, while still catching injected drift.
  • The scheduled GitHub Actions job is verified running end to end. A full 25-batch demo run takes roughly 5 to 15 minutes.

Limits

  • A 25-batch demo produces only one or two promotions, so rollback usually has no prior champion to revert to. The mechanism is tested but rarely exercised live.
  • The model is a plain logistic regression on purpose. The governance loop around it is the deliverable.

Causal Inference

Causal Impact & Heterogeneous Response Analysis

Validates four causal estimators against known ground truth before trusting any of them on a real segment-level question.

+210%naive OLS bias at strong confounding
2.6%IPW bias at the same severity
34automated tests

Overview

On the Criteo Uplift dataset (about 14 million rows from a randomized ad experiment), a subsample is artificially confounded so naive OLS, matching, IPW, and AIPW can each be checked against a known ground-truth effect before any of them touches a real segment question.

How it works

  • A minimum-detectable-effect calculation, not a default, chose the visit outcome over the far rarer conversion outcome for segment work.
  • A calibrated T-learner estimates individual effects and is scored against random targeting with the Qini coefficient, which came out at 0.0565.
  • Benjamini-Hochberg correction and per-segment power analysis test whether each segment finding is defensible at its own sample size.

Guardrails

  • Rosenbaum bounds give a critical Gamma of 1.15: a confounder shifting treatment odds by about 15% would overturn the matched-pairs result, so it is fragile.
  • The one LLM step critiques diagnostics and falls back from Groq to NVIDIA NIM to a rule-based critique. It never touches an estimate or a p-value.
  • Checks on row count, columns, and treatment split fail loudly on drift instead of continuing silently.

Results

  • Naive OLS bias grew from -8.6% with no confounding to +210% at strong severity.
  • IPW and AIPW stayed within about 3 to 7% of ground truth at moderate and strong severity, but were 10 to 26% off with none or mild confounding.
  • 1:1 matching stayed 18 to 37% below ground truth at every severity, because it matches only 18% of treated units and estimates the effect on that subset.
  • Three of four segments stay significant after correction, but the two largest effects, 4 to 6 times the aggregate, come from small segments that are underpowered.

Limits

  • Rosenbaum bounds cover matching only. There is no equivalent check for IPW or AIPW.
  • The heterogeneity model is a T-learner. Causal forests are future work.

Experimentation

Experiment Design & Power Analysis for a Shipping Policy Change

A preregistered A/B pipeline where the metric, MDE, sample size, and tests are locked before any experimental data exists.

2,499sellers per arm required
R$29.02estimated lift, true value R$28.00
23automated tests

Overview

Calibrated from the public Olist e-commerce dataset (values in Brazilian reais, R$) but simulated end to end. A population with a known injected effect is randomized and analyzed with exactly the tests locked into a preregistration before the simulation runs.

How it works

  • Sellers, not orders, are the randomization unit, since a seller's orders are not independent of each other.
  • A guardrail metric, delivery-complaint rate, is tested for non-inferiority against a 2.0pp margin, so a revenue win cannot mask a satisfaction loss.
  • An AST-level test verifies that the raw data and the injected effect can never reach the analysis or reporting code.

Guardrails

  • analyze() raises an error unless it receives exactly the preregistered 2,499 sellers per arm, which rules out peeking and stopping when p drops below 0.05.
  • A mutation test deliberately breaks randomization and confirms the ground-truth recovery check catches the error.

Results

  • AOV lift: estimated R$29.02 (95% CI R$21.12 to R$36.91) against an injected R$28.00. The interval contains the true value.
  • Complaint rate: estimated +1.60pp (95% CI +1.27 to +1.93) against an injected +1.20pp. The interval narrowly misses, consistent with the roughly 5% miss rate of a 95% interval.
  • The guardrail decision holds: the whole interval sits inside the 2.0pp margin.

Limits

  • One seeded run, not proof the method generalizes to other effect sizes or marketplaces.
  • The guardrail test pools order-level counts instead of clustering by seller, which is slightly anti-conservative.

Customer Churn Prediction with Profit Optimization

Predicts churn, then decides who to target by expected profit rather than a raw probability cutoff.

1.07Mraw transaction records
12RFM features per window
31unit tests

Overview

Predicts 90-day churn from a customer's transaction history, calibrates the score into a probability, and flags INTERVENE only when expected profit clears the offer cost. XGBoost is tuned and calibrated on an earlier validation period, and the final test period is used once.

How it works

  • Sliding 365-day observation and 90-day prediction windows let one customer contribute several labeled examples across time.
  • Expected profit is churn probability times success rate times three months of spend, minus offer cost, so a high-risk, low-spend customer can be left alone.
  • A SHAP waterfall explains each single-customer prediction in the dashboard and never touches training or thresholding.

Guardrails

  • The split is asserted chronological and non-overlapping, with regression tests. Hyperparameters, calibration, and the profit threshold are all fixed before the test period is used.
  • Cancellations are netted against the specific invoice and line item they credit, tested against duplicate and multi-cancellation cases.
  • Dashboard tabs check for their artifacts first and show a run-the-pipeline message instead of a traceback.

Evaluation

PR-AUC is used over ROC-AUC on purpose, since ROC-AUC flatters class-imbalanced data. Final PR-AUC, Brier score, and profit lift are generated at run time and are not published here yet. The offer cost (£10) and success rate (15%) are configured assumptions, not measurements.

Limits

  • The intervention success rate is a configured constant. In production it would come from an A/B test.
  • Cold-start customers with no transaction history cannot be scored.

Forecasting

RetailCast: Forecasting and Anomaly Bench

Retail demand forecasting and anomaly detection benchmarked across four models, with grounded, verified LLM reporting.

0.632best MASE, XGBoost
60retail series benchmarked
20automated tests

Overview

Benchmarks Prophet, SARIMA, LightGBM, and XGBoost with expanding-window walk-forward validation on 60 retail series (SARIMA on 3), adds two anomaly detectors, and generates an LLM report whose numeric claims are checked against source data.

How it works

  • Heavy computation runs on Kaggle's free notebooks. A lightweight local Streamlit dashboard reads only the saved notebook outputs.
  • Every numeric claim in the LLM report is regex-checked against source facts before display, with provider fallback across Groq, NVIDIA NIM, and Gemini.
  • Metrics live in one module and are synced byte for byte into the two notebooks that cannot import it, with a test that fails if they drift.

Guardrails

  • Isolation Forest's evaluation features are scaled from clean pre-injection statistics. Computing them on the injected data had silently inflated its apparent precision.
  • Cost-of-error figures are labeled illustrative, built from published grocery margin benchmarks rather than verified P&L data.

Results

  • XGBoost led the 15-day holdout with MASE 0.632, MAPE 15.23%, and WAPE 11.76%. LightGBM followed at 0.674. Prophet (1.001) and SARIMA (1.019) landed near or above a naive lag-7 baseline.
  • Isolation Forest scored precision 0.867, recall 0.78, and F1 0.821. Control limits scored precision 0.581, recall 0.86, and F1 0.694: slightly more anomalies caught, but many more false positives.

Limits

  • This is backtesting on a 15-day holdout with known actuals, not live forecasting. SARIMA ran on 3 series, so its average is not like for like.
  • The grounding check is regex-based and can ground a hallucinated figure against an unrelated correct one.

ReelBench: Multi-Stage Recommender Benchmark

Five recommendation approaches benchmarked head to head on MovieLens 25M under one evaluation harness.

5approaches compared
1.4GBitem-item CF peak memory (synthetic ML-25M scale)
0live model calls at request time

Overview

Popularity, item-item CF, ALS/BPR, a two-tower retriever, and SASRec are scored through one leakage-tested harness on MovieLens 25M. The harness was built and unit-tested before any model existed.

How it works

  • A single global timestamp cutoff splits train and test. A per-user-only split can pass for every user while still leaking future signal across users.
  • Two-tower and SASRec embeddings feed a FAISS index, and a LightGBM ranker re-scores the survivors on similarity, recency, popularity, user activity, and genre match.
  • Cold-start items get a separate FAISS index built from local title and genre embeddings, because those embedding spaces cannot be merged with the learned ones.

Guardrails

  • Row-blocked sparse similarity kept item-item CF at about 1.4GB peak on synthetic data at ML-25M scale (62,423 items, 162,541 users), against about 15GB for a dense matrix.
  • Both neural models checkpoint every epoch and resume, since free-tier GPU sessions can disconnect mid-training.
  • Ranker features were rebuilt on a second temporal split after an earlier version leaked the label slice.

Results

  • The comparison table is the deliverable, but the copy committed to the repo is synthetic demo output, not a real MovieLens 25M evaluation.
  • On a full real run, the two-tower's recall@10 came in below the popularity baseline, consistent with an under-trained model at 10 epochs and 64 dimensions.

Limits

  • MovieLens 25M is a static historical snapshot, so the table reflects relative model quality on that snapshot, not current taste.
  • The two-tower uses no content features, so it generalizes to unseen users and items no better than ALS.
