Competitive Intelligence Agent

An autonomous research agent that turns a company name into a sourced, traceable intelligence brief.

5
required brief fields
3
max replan cycles
15
company eval benchmark
Overview

Given a company or product name, a four-role pipeline plans research sub-questions, executes web search and calculation tools, critiques its own coverage against five required fields, and synthesizes a final brief with numbered citations. Anything it cannot source is marked insufficient information rather than invented.

How it works
  • Planner, Executor, Critic, and Synthesizer each run on a different model and provider, matched to that role's actual call volume against free-tier rate limits rather than picked for variety.
  • The Critic checks coverage against the five required fields and can send the run back to re-plan up to three times before handing off to the Synthesizer.
  • Hard stops cap a run at 3 replans, 15 tool calls, and 8 minutes of wall clock time. On any limit the run returns whatever it confirmed and marks the rest insufficient information.
Guardrails
  • Every search result is wrapped in untrusted-content delimiters before reaching a prompt, a direct mitigation against prompt injection from open-web content.
  • Postgres-backed memory seeds a run from an exact entity match under 7 days old, but never auto-seeds on a fuzzy match, avoiding conflating similarly named companies.
  • Per-step failure isolation keeps a single blocked research step from crashing the run, and the Synthesizer falls back to a plain scratchpad-built report if its own LLM call fails.
Results

An evaluation harness scores groundedness and completeness with an isolated judge model across a 15-company benchmark, and an ablation study measures the Critic loop's actual effect on output quality rather than assuming the extra latency is worth it.

Continuous Credit Risk Governance Pipeline

A self-governing pipeline that scores, drift-checks, retrains, gates, and rolls back a credit risk model with no human in the loop.

637
simulated live batches
3
promotion gates
54
automated tests
Overview

Simulates the part of the ML lifecycle a portfolio project usually skips: what happens after deployment. Each cycle scores a live batch, releases delayed ground-truth labels, checks for distribution drift, and, if warranted, retrains a challenger and gates it against the current champion before promoting or rejecting it.

How it works
  • A three-gate promotion system, tolerance band, dominance, and statistical significance via McNemar or a bootstrap confidence interval, separates a genuine improvement from sampling noise on batches of roughly 200 rows.
  • Rollback is held to the same rigor as promotion: a raw point-estimate drop is not enough, the bootstrap interval's upper bound has to confirm a real performance decline.
  • Every governance decision, promotions, rejections, drift checks, and rollback checks, is written to an audit log, not only the ones that changed something.
Guardrails
  • The drift threshold is empirically tuned: 3 or more of 10 flagged features cuts false retrain triggers to roughly 1 percent of undrifted batches while still catching real injected drift.
  • Optimistic concurrency claims a batch before any work starts, so concurrent scheduled and manual runs cannot create duplicate predictions.
  • The true label is never stored alongside model input features, closing a leakage path a delayed-label design would otherwise be exposed to.
Results

Runs on a schedule via GitHub Actions, with model artifacts tracked through MLflow and data versioned through DVC, verified running end to end on a real schedule rather than only in a local demo.

Kubernetes Gated RAG

A production-oriented RAG system for Kubernetes Q&A that answers only from ingested docs, defended in depth.

2
cache layers
3
provider failover chain
6
RAGAS eval metrics
Overview

Every question passes through a safety gate and a topic gate before a generation call is spent, then through hard relevance thresholds on retrieval, and the generated answer itself is safety-checked again before it is shown or cached.

How it works
  • Two layers of caching, exact match then semantic similarity, are both version-filtered so a policy or corpus change automatically invalidates stale answers.
  • Generation fails over across three provider links, Groq, a secondary Groq account, then NVIDIA NIM, on the same model string, so the failover is about separate rate-limit budgets, not model diversity.
  • Any infrastructure failure, a timeout, a reranker crash, every provider being down at once, is surfaced as temporarily unavailable and is never cached, so a transient outage cannot get baked in as a wrong answer.
Guardrails
  • Fail-closed safety: known jailbreak patterns are blocked locally first, everything else goes through a guarded classifier with a timeout and circuit breaker, and an unusable verdict blocks the request by default.
  • Rewritten, history-dependent questions are rechecked for jailbreak patterns rather than trusting the first-turn safety check alone.
  • Only rerank-approved chunks reach generation. A reranker crash is treated as an infrastructure failure, never a silent pass-through.
Results

Evaluated with a Ragas harness across faithfulness, answer relevancy, and context precision and recall, judged by a model from a separate family than anything used in the live pipeline.

ReelBench: Multi-Stage Recommender Benchmark

Five recommendation approaches benchmarked head to head on MovieLens 25M under one evaluation harness.

5
approaches compared
62k
catalog items handled
<1.4GB
peak memory at scale
Overview

Popularity, item-item collaborative filtering, ALS/BPR, a two-tower neural retriever, and SASRec are all scored through one identical, leakage-tested evaluation harness, built and unit-tested before any model existed.

How it works
  • A single global timestamp cutoff splits train and test, not a per-user-only split, which can look correct per user while still leaking future signal across users.
  • Two-tower and SASRec embeddings feed a FAISS retrieval index; a LightGBM ranker re-scores survivors on similarity, recency, popularity, and genre match, all served from cached artifacts with no live model calls at request time.
  • A cold-start path embeds movie titles and genres once with a local sentence-transformer model, giving zero-interaction items a content-based path independent of the main retrieval space.
Guardrails
  • Sparse, row-blocked similarity keeps item-item CF's peak memory under 1.4GB at full catalog scale, against roughly 15GB for a naive dense similarity matrix.
  • Both neural models checkpoint every epoch and resume automatically, since free-tier GPU sessions can disconnect without warning mid-training.
  • Ranker training features are built from a second temporal split applied only to outer train, after an earlier version was found to leak the label slice into ranker features.
Results

The evaluation comparison table is the deliverable, not the model count. Every approach in it was scored through the same harness on the same held-out split, with a leakage assertion that runs before any model is trained.

Customer Churn Prediction with Profit Optimization

Turns churn probability into a per-customer intervene or do-not-intervene call based on expected financial gain, not a raw cutoff.

12
RFM features per window
31
unit tests
90-day
churn lookahead
Overview

XGBoost is tuned on an earlier validation period, calibrated with isotonic regression on that same pre-test period, and the profit threshold is swept and locked before the final chronological test period is ever touched.

How it works
  • Sliding 365-day observation and 90-day prediction windows let the same customer contribute multiple labeled examples across time, instead of one static snapshot.
  • An expected-value formula, probability of churn times intervention success rate times monthly spend, minus intervention cost, decides who gets targeted, so a high-risk, low-spend customer can be correctly left alone.
  • A SHAP waterfall explains every single-customer prediction in the dashboard, without touching training, tuning, or thresholding.
Guardrails
  • Cancellation netting only decrements the specific invoice and line item it matches, verified against duplicate and multi-cancellation edge cases, not only the common case.
  • Every dashboard tab checks for its required artifact before rendering, and shows a run-the-pipeline message instead of a raw traceback.
Results

PR-AUC is used over ROC-AUC on purpose, since ROC-AUC inflates apparent performance on this class-imbalanced churn rate by rewarding correct ranking of the abundant negative class.

Causal Impact & Heterogeneous Response Analysis

Validates four causal estimators against known ground truth before trusting any of them on a real segment-level question.

14M
rows of randomized exposure data
4
estimators stress-tested
34
automated tests
Overview

On the Criteo Uplift dataset, a subsample is artificially confounded so naive OLS, propensity score matching, IPW, and AIPW can each be checked against a known ground-truth effect before any of them touches a real segmentation question.

How it works
  • A minimum-detectable-effect calculation, not a default, decides that the heterogeneity analysis uses the visit outcome instead of the far rarer conversion outcome.
  • A calibrated T-learner estimates individual treatment effects, evaluated honestly against random targeting via the Qini coefficient rather than assumed correct because it ran.
  • Benjamini-Hochberg correction and per-segment power analysis check whether each significant segment finding is even statistically defensible at its own sample size.
Guardrails
  • Rosenbaum bounds quantify exactly how much unmeasured confounding, roughly a 15 percent shift in treatment odds, would be needed to overturn the matched-pairs conclusion.
  • The one LLM step in the pipeline, a diagnostic critique of balance and sensitivity outputs, falls back from Groq to NVIDIA NIM to a deterministic rule-based critique, and never touches the analysis itself.
Results

IPW and AIPW stayed within roughly 3 to 8 percent of the ground-truth effect across every confounding severity tested, while naive OLS bias grew past 200 percent at the strongest severity.

Experiment Design & Power Analysis

A preregistered A/B test pipeline for a shipping policy change, with the metric, sample size, and tests locked before data exists.

2,499
sellers per arm required
23
automated tests
R$28

Overview

Calibrated from the real Olist e-commerce dataset but entirely simulated end to end: a population with a known injected effect is created, randomized, and analyzed with exactly the tests locked into a preregistration document before the simulation ever runs.

How it works
  • Sellers, not orders, are the randomization unit, avoiding a violation of the no-interference assumption within a single seller's order stream.
  • A guardrail metric, the delivery-complaint rate, is tested for non-inferiority alongside the primary average-order-value lift, so a revenue win cannot quietly mask a satisfaction loss.
  • Dataset-role enforcement, checked at the AST level, verifies the raw data and the known injected effect can never reach the analysis or reporting code.
Guardrails
  • The analysis function raises an error unless it receives exactly the preregistered sample size, preventing repeated interim peeking and stopping the moment a result looks significant.
  • A mutation test deliberately breaks randomization and confirms the ground-truth recovery check actually catches the resulting error.
Results

The preregistered analysis recovered the injected order-value lift within its confidence interval, and the guardrail decision held even though that interval narrowly missed the injected complaint-rate value, consistent with the miss rate expected from a 95 percent interval.

RetailCast: Forecasting and Anomaly Bench

Benchmarks four forecasting models and two anomaly detectors across 60 retail series, with grounded, verified LLM reporting.

Overview

A global XGBoost model pooling across all 60 series beat per-series statistical baselines on average error, at the cost of series-specific interpretability, while Prophet and SARIMA landed near or above a naive seasonal baseline.

How it works
  • Heavy computation runs on Kaggle's free GPU notebooks; a lightweight local Streamlit dashboard reads only the committed notebook outputs, never recomputing results from a different source.
  • An LLM narrative report verifies every numeric claim it makes against the underlying source data before it is displayed, with automatic provider fallback across Groq, NVIDIA NIM, and Gemini.
Guardrails
  • Isolation Forest's evaluation features are scaled from clean, pre-injection statistics rather than statistics computed on the injected anomalies themselves, which had been silently inflating its apparent precision.
  • A synced constants script keeps the shared metrics module and its two notebook copies byte-identical, with a test that fails the suite if a change is forgotten.
Results

Isolation Forest reached 0.867 precision and 0.821 F1 on synthetic-injection evaluation, against 0.581 precision for simple control limits, which still caught slightly more injected anomalies at the cost of far more false positives.

IssueOps MCP

A guarded MCP server for GitHub issue triage. Every mutating action is proposed, never executed, without a human approval step.

10
model-facing tools
0
execute tools on that surface
48h
proposal expiry window
Overview

Ten tools sit on the model-facing surface: five read-only, five that only ever queue a proposed comment, label, assignment, or close for a human to review. No execute or confirm tool exists anywhere on that surface, for any client.

How it works
  • The GitHub write credential lives in exactly one process, the human-facing approval dashboard, and is actively dropped from every other process's environment even when it was never injected there.
  • Before executing an approved action, the dashboard re-fetches the issue's live state and compares it against the snapshot taken at proposal time, marking the action stale instead of executing against outdated context.
  • Every read, proposal, approval, rejection, and execution writes to an audit log, so the log reflects what actually happened on GitHub, not only what was attempted.
Guardrails
  • An identical pending proposal is deduplicated rather than inserted twice, and proposals older than 48 hours auto-expire rather than executing later against a stale issue.
  • A heuristic prompt-injection phrase flag is surfaced in the dashboard as an advisory signal only. It is never checked in the approval or execution path and is explicitly not treated as a security boundary.
Results

An execution-level guarantee check runs a direct SQL query confirming every completed GitHub mutation in the audit log is backed by an approved, human-authorized proposal. That number is required to be zero.
