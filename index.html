GenAI / RAG

Kubernetes Gated RAG

A Kubernetes Q&A system that answers only from the docs you ingest, with a gate at every stage that could let a bad answer through.

0.95faithfulness on the 8-row starter set
3generation failover links, same model
2cache layers, exact and semantic

Overview

Most RAG demos stop at retrieve and generate. This one gates every stage: safety and topic checks run before any generation call, retrieval must clear a hard rerank threshold or the system says it has no grounded docs, and answers are safety-checked again before they are shown or cached.

How it works

  • Two caches, exact then semantic, sit in front of retrieval. Keys include schema, policy, and corpus versions, so re-ingesting or changing a policy invalidates stale answers.
  • Generation fails over across Groq, a second Groq account, and NVIDIA NIM on the same model, for separate rate-limit budgets rather than model diversity.
  • Ingestion filters files with an LLM relevance gate and uses deterministic IDs, so edits replace rather than duplicate.

Guardrails

  • Known jailbreak patterns are blocked locally and the rest goes to NeMoGuard. Every safety check and provider has its own circuit breaker, and a classifier outage returns a temporarily unavailable response, never a pass.
  • Rerank fails closed: only chunks scoring 0.5 or higher reach the generator. Infrastructure failures are never cached or reported as policy refusals.

Results

  • On the 8-row starter set: faithfulness 0.95, answer relevancy 0.91, context precision 1.00, context recall 0.94, context entity recall 0.90, semantic similarity 0.91.
  • The judge (gemini-3.5-flash) comes from a different model family than the generator (gpt-oss-120b on Groq). This shows the harness runs end to end. It is not a benchmark.

Limits

  • Eval rows bring hand-written contexts, so the retriever, gates, and caches are not scored. Eight rows support no strong conclusions, and guardrails are verified only by unit tests.
  • Ingested chunks enter the prompt unfiltered, the jailbreak regexes are English-only, and caches are single-host.

AI Agents

Competitive Intelligence Agent

An autonomous research agent that turns a company name into a sourced intelligence brief, and marks anything it cannot source as unknown.

+1.0completeness gain from the Critic loop (0 to 5, n=5)
+0.8groundedness gain from the Critic loop (0 to 5, n=5)
3max replan cycles

Overview

Given a company name, the agent plans research across five fields (what it does, funding and ownership, recent news, competitors, risks) and writes a brief where every claim has a numbered citation. A Critic reviews coverage and can send it back to re-plan. A paired ablation measures what that loop buys and what it costs.

How it works

  • Each role runs on a different free-tier model: Nemotron 3 Super plans, gpt-oss-120b executes, Gemini 3.5 Flash-Lite critiques, and Gemini 3.5 Flash writes the brief. Critic and Synthesizer differ so they draw on separate quotas.
  • The Critic can loop back to the Planner up to 3 times, each replan targeting only flagged gaps. With the Critic disabled, the node is removed from the graph, which keeps the ablation clean.
  • Postgres memory reuses fields under 7 days old, except recent news, which is always re-researched.

Guardrails

  • Hard stops at 3 replans, 15 tool calls, 8 steps per plan, and 8 minutes. On any limit the run returns what it confirmed and marks the rest insufficient information.
  • Search results are treated as untrusted, and a field cannot be marked confirmed without evidence. If the Synthesizer fails, a plain report is built with no LLM and never cached.

Results

  • On 5 hand-picked companies (Anthropic, Stripe, Notion, Figma, Databricks), a Groq judge scored groundedness 4.6 with the Critic against 3.8 without, and completeness 4.8 against 3.8.
  • The cost: about 10.8 tool calls against 6.2 and roughly 96 seconds against 40, or about 1.7x the calls and 2.4x the time.

Limits

  • n=5 is a smoke test, and one noisy judge call can move an average by 0.2. The full 15-company benchmark needs 30 Synthesizer calls against roughly 20 requests per day, so free-tier quotas block it.
  • Citations prove provenance, not reliability, since search snippets get no credibility filtering. The API has no rate limiting and the Streamlit UI has no authentication.

AI Agents / MCP

IssueOps MCP

A GitHub issue triage server where the model can only propose. Nothing reaches GitHub until a human approves it.

10MCP tools: 5 read, 5 propose
0execute tools exposed to the model
48hproposal expiry window

Overview

An MCP client such as Claude, or a triage agent, can read GitHub issues and propose comments, labels, assignments, and closes. Ten tools face the model: five read-only and five that only queue a proposal in Postgres. No execute tool exists. A person reviews each proposal in a Streamlit dashboard, and every read, proposal, and decision is audit-logged.

How it works

  • The GitHub write token lives in one process only, the dashboard.
  • Approval claims the proposal atomically, so concurrent approvals cannot double execute. The issue is then re-fetched, and the proposal goes stale if the issue changed, a close target is no longer open, or an identical comment already exists.
  • The triage agent uses the same propose path. It classifies issues with gpt-oss-20b on Groq and is limited to labels and assignments unless comments and closes are explicitly enabled.

Guardrails

  • Proposals are validated before queuing: repo allowlist, pull requests rejected, caps of 10 per issue and 500 per initiator, and dedup of identical pending proposals.
  • A network error or 5xx mid-write is recorded as needs_review, never auto-retried. Unapproved proposals expire after 48 hours.
  • Issue text is untrusted. A heuristic injection flag gives the approver a hint, but the real control is that every proposal needs human approval.

Results

  • On a 12-issue fixture (9 legitimate, 3 adversarial): label accuracy 9 of 9, no injected marker echoed in output, and about 4.2 seconds of model latency per issue.
  • All 3 adversarial issues still produced a proposal. That may be correct spam triage or obedience, and the metric cannot tell them apart, but a human approval stands in front of GitHub either way.
  • CI runs integration tests on Postgres 16 covering concurrent approvals and deadlock freedom.

Limits

  • Approver identity is a typed name, not authentication, and all processes share one Postgres role, so the audit log is append-only by convention only.
  • n=12 is a smoke test, not a security or accuracy benchmark. Expiry runs only when the dashboard loads, and issue text is sent to Groq and stored in Neon.

MLOps

Continuous Credit Risk Governance Pipeline

A credit-risk model that runs its own lifecycle: it scores, watches for drift, retrains, gates its own promotions, and rolls itself back.

1%false retrains on undrifted batches (was about 40%)
3promotion checks: tolerance, dominance, significance
105automated tests

Overview

A model does not stay good because it was good at launch. This pipeline simulates life after deployment on the Give Me Some Credit dataset: a recession is injected into 318 live batches of 200 rows, and the pipeline must notice, challenge the champion, and replace it with no human in the loop. A GitHub Actions cron advances the clock every 3 hours.

How it works

  • A challenger is promoted only if it passes three ordered checks: no worse than the champion by more than 0.01 AUC-PR, better outright, and a 2,000-resample bootstrap CI on the AUC-PR delta that clears zero.
  • Drift uses a per-feature K-S test with a 3-batch cooldown. K-S is forced because Evidently otherwise switches to Wasserstein above 1,000 reference rows and misses heavy tails. The challenger trains on 3,000 base rows plus up to 6,000 recent labeled rows and is gated on a labeled batch it never saw.
  • Rollback is decided by a paired bootstrap of the previous champion against the current one on the same live batch.

Guardrails

  • Labels arrive after a 3-batch delay and are never stored beside model inputs. Retrains exclude the gate batch.
  • Postgres decides the champion, and every tick starts by resetting MLflow's @production alias to it. A failed tick rolls back and retries cleanly. Every decision, including rejections, is audit-logged.

Results

  • Raising the drift-share threshold from 0.1 to 0.3 cut false retrains on undrifted batches from about 40% to about 1%.
  • The 25-tick demo covers persistent drift from batch 10 and temporary drift in batches 15 to 19, and ran in about 90 seconds.
  • 105 tests include end-to-end leakage, cooldown, and rollback checks, with integration tests against Postgres 16 in CI.

Limits

  • With about 200 rows and 13 positives per batch, confidence intervals are wide, so real improvements are often rejected and rollback rarely has an earlier champion to compare.
  • Drift is measured on the current batch but labels belong to an earlier one, and K-S detection power on 200 rows is unmeasured.
  • The model is a deliberately plain logistic regression, because the loop around it is the deliverable. Models are stored as pickles, which is safe only with a trusted remote.

Causal Inference

Causal Impact & Heterogeneous Response Analysis

Tests four causal estimators against a full-data reference effect before trusting any of them on a real segment-level question.

+417%naive OLS bias at strong confounding
0.0565Qini coefficient, 95% CI 0.030 to 0.085
1.12critical Gamma, fragile to hidden bias

Overview

The Criteo Uplift dataset holds 13,979,592 rows from a randomized ad experiment. Even there, the raw difference in means overstates the covariate-adjusted reference effect (0.00715, 95% CI 0.00689 to 0.00740) by 45%, so the benchmark is a cross-fitted AIPW estimate on all rows. A subsample is then confounded on purpose to test whether naive OLS, matching, IPW, and AIPW recover that reference. Only then does it ask which audiences responded.

How it works

  • Confounding is induced by a retention rule on the covariate most correlated with the outcome, calibrated until the naive estimate misses the reference, then repeated over 20 independent 300,000-row replicates.
  • A minimum-detectable-effect calculation chose visit over conversion as the outcome: the conversion effect sits right at its MDE, too coarse for per-segment estimates.
  • A calibrated T-learner is judged against random targeting with a bootstrapped Qini coefficient. Users are clustered with KMeans, and each segment gets a cross-fitted AIPW effect with Benjamini-Hochberg correction and a Cochran Q heterogeneity test.

Guardrails

  • All estimators share one cross-fitted propensity and one trimmed population, naive OLS included.
  • Rosenbaum bounds report how much hidden confounding would overturn the result. A critical Gamma below 1.5 is classed fragile.
  • The one LLM step critiques balance diagnostics and never touches an estimate or p-value.

Results

  • Naive OLS bias grew from +44% with no confounding to +417% at strong severity. IPW and AIPW stayed within 8% through mild confounding, but at strong severity PSM sat 43% below the reference, IPW 47% above, and AIPW 36% below.
  • The T-learner's Qini coefficient is 0.0565 (95% CI 0.0301 to 0.0854), better than random targeting. Two of four segments stay significant after correction: a 4.8% segment at 0.0368 and the 39.4% segment at 0.0065.
  • Critical Gamma is 1.12, so a hidden confounder shifting treatment odds by about 12% would overturn the matched result. That speaks to whether an effect exists, not its size.

Limits

  • The reference rests on ignorability given 12 covariates. AIPW (0.00715) and IPW (0.00780) differ by more than the reference interval, so the true effect is only pinned to roughly 0.0071 to 0.0078.
  • Bias curves are specific to this covariate, retention rule, and replicate count. Segment inference is approximate, and Rosenbaum bounds are PSM-only.
  • Notebook logic, the data loader, the T-learner, and the dashboard are untested.

Experimentation

Experiment Design & Power Analysis for a Shipping Policy Change

A preregistered A/B pipeline in which the metric, minimum detectable effect, sample size, and tests are locked before any experimental data exists.

2,503sellers per arm required
2.0ppcomplaint-rate guardrail margin, frozen up front
71automated tests

Overview

Calibrated from the public Olist e-commerce dataset but simulated end to end. The question: does free shipping raise average order value (AOV) without raising complaint rates? The design, including a 2.0 percentage point non-inferiority margin on complaints, was committed before any simulation code existed. A population with a known injected effect (BRL 28.00 AOV, +1.2pp complaints) is then randomized and the preregistered tests run once.

How it works

  • Sellers, not orders, are the randomization unit, since a seller's orders are not independent.
  • The primary test is a Welch t-test on seller AOV with a BRL 25 minimum lift. The complaint guardrail is a one-sided, margin-shifted z-test returning passed, breached, or inconclusive.
  • A GO needs a significant lift of at least BRL 25 and a passed guardrail, so a revenue win cannot mask a satisfaction loss.

Design integrity

  • The analysis raises an error unless each arm has exactly 2,503 sellers, which rules out peeking and stopping when p drops below 0.05. A second analysis on different data raises an error instead of overwriting.
  • AST tests verify that raw Olist data, the injected effect, and the counterfactual never reach analysis code. The guards catch accidental drift, not tampering. Git history is the real lock.

Results

  • NO-GO, because the guardrail is inconclusive, not breached. Mean seller AOV rose from BRL 134.02 to BRL 172.09 (p = 8.6e-06), clearing the minimum.
  • Complaints rose from 12.18% to 13.90%, a 1.73pp gap under the 2.0pp margin, but the margin-shifted test (one-sided p = 0.163) did not establish non-inferiority.
  • Both injected effects were recovered: AOV lift BRL 38.07 (95% CI 21.32 to 54.82) and complaints +1.73pp (95% CI 1.18 to 2.27). This reflects limited precision, not harm: post hoc power is about 75% at the realized 1.35pp gap.

Limits

  • Guardrail sizing is approximate: the 142 sellers-equivalent per arm ignores within-seller correlation.
  • Recovery is a smoke test, since one seeded run does not show the method generalizes. Baselines reflect Olist's category mix and the Brazilian market.

Data Science

Customer Churn Prediction with Profit Optimization

Predicts churn, then decides whom to target by expected profit instead of a raw probability cutoff.

1.07Mraw transaction records
12RFM features per window
70offline unit tests

Overview

Predicts 90-day churn from transaction history on the Online Retail II dataset and calibrates the score into a real probability. A customer is flagged INTERVENE only when expected profit clears the offer cost: churn probability times success rate times three months of spend, minus cost. A high-risk, low-spend customer can correctly be left alone.

How it works

  • Sliding 365-day windows with a 90-day horizon and a 30-day slide give each customer several labeled examples, with 12 features per window covering recency, frequency, spend, trend, and purchase intervals.
  • XGBoost is tuned with Optuna on one half of validation (split by customer ID parity) and calibrated on the other half, so no role sees another's data. The test period is used once.
  • A SHAP waterfall explains each prediction in the dashboard and never touches training or thresholding.

Leakage controls

  • The split is chronological with a 90-day embargo at each boundary, which purges 17,329 rows (40.3%) of the data. Ordering, disjointness, and the gap are asserted in tests.
  • Credits are dated at the credit note, and cancellations never count as a purchase when labeling churn.

Results

  • On the final temporal test, PR-AUC was 0.7452 and the Brier score on calibrated probabilities was 0.2073.
  • Net campaign profit, under an assumed offer cost and success rate: £4,433 for random 20% targeting, £9,648 for a 0.5 cutoff, £16,817 for the profit-optimized global threshold, and £23,618 for the per-customer expected-value rule.
  • The locked threshold is 0.01, so the global policy is close to blanket targeting and its edge over the 0.5 cutoff comes mainly from contacting more people. The expected-value rule's lead is partly by construction.

Limits

  • Only about 10 windows exist, so after the embargo roughly 4 go to train and 1 each to validation and test. Profit figures rest on one period with no confidence interval, and no contact-everyone baseline is reported.
  • Overlapping windows and recurring customers likely make metrics optimistic. The success rate is a configured constant where production would use an A/B test.
  • The 70 tests run on synthetic fixtures and check code and leakage controls, not model quality.

DemandLens: Retail Demand Forecasting and Anomaly Benchmark

Retail demand forecasting and anomaly detection benchmarked across four models, with an LLM report whose every number is checked against source data.

60retail series benchmarked
0.974best holdout MASE, LightGBM, within 0.04 of two rivals
52automated tests

Overview

Benchmarks Prophet, SARIMA, LightGBM, and XGBoost on 60 retail series with a 15-day holdout, adds control-limit and Isolation Forest anomaly detectors, and generates an LLM report. Heavy computation runs in free Kaggle notebooks, and a light Streamlit dashboard reads only their saved outputs.

How it works

  • ML features use lags of at least 21 days, and rolling statistics and oil price are shifted by the forecast horizon, so no feature sees in-window actuals. The final model is chosen on mean MASE over 4 cross-validation folds, not the holdout.
  • Every numeric claim in the LLM report is regex-checked against source facts before display, with fallback across Groq, NVIDIA NIM, and Gemini.

Guardrails

  • Anomaly evaluation injects 50 spikes and drops into 900 holdout rows, so scores are measured against known ground truth.
  • Cost-of-error figures (about $224,480 for XGBoost against $225,702 for LightGBM) are illustrative, using assumed grocery margins.

Results

  • No model wins clearly. LightGBM scored MASE 0.974, Prophet 0.996, and XGBoost 1.011, all within 0.04, with no significance test. SARIMA ran on only 3 series, where the ranking is Prophet 0.793, SARIMA 0.838, LightGBM 0.919, XGBoost 0.933.
  • Control limits scored F1 0.832 (precision 0.824, recall 0.84). Isolation Forest scored F1 0.681 (precision 0.527, recall 0.96): it caught 48 of 50 but flagged about 43 clean rows, by construction of its 5% contamination setting.
  • XGBoost was selected on cross-validation (0.866 against 0.902 for LightGBM) even though LightGBM scores slightly better on the holdout. The choice is reported as made, not retrofitted.

Limits

  • This is backtesting on a 15-day holdout, not live forecasting, and promotion and holiday flags are assumed known at forecast time.
  • The grounding check is regex-based, so it misses paraphrases and can ground a wrong figure against an unrelated correct one.
  • Anomaly scores measure detectability of injected anomalies, not performance on real incidents.

Recommender Systems

ReelBench: Multi-Stage Recommender Benchmark

Five recommendation approaches scored head to head on MovieLens 25M through one leakage-tested evaluation harness.

0.0485Recall@10 for SASRec + ranker, against 0.0243 for popularity
5approaches compared
0external calls at request time

Overview

A two-stage recommender, candidate retrieval then ranking, trained on free-tier GPUs and served entirely on CPU. The comparison table is the deliverable. The harness was built and unit-tested before any model existed, so popularity, item-item CF, ALS, a two-tower retriever, and SASRec are all scored by the same code on the same held-out split of 12.45M implicit interactions.

How it works

  • A single global timestamp cutoff splits train and test. A per-user split can look correct for every user while leaking future signal across users, and a unit test shows the difference.
  • Two-tower and SASRec embeddings feed a FAISS index, and a LightGBM LambdaRank model re-scores the survivors. Ranker labels come from a second temporal split inside train, so the test set is never touched.
  • Serving never calls a model: FastAPI and Streamlit read cached artifacts only. Cold-start items get a separate FAISS index built from title and genre embeddings.

Guardrails

  • assert_no_leakage() hard-fails on train rows at or after the cutoff, test rows before it, or test users absent from train.
  • Item-item CF computes similarity in row blocks, since a dense matrix over the 31,195-item catalog would need about 3.9GB at float32.
  • Both neural models checkpoint every epoch and resume after free-tier GPU disconnects.

Results

  • SASRec + ranker leads every accuracy metric: Recall@10 0.0485, NDCG@10 0.0432, Recall@20 0.0832. ALS is the strongest single-stage model at Recall@10 0.0376, and popularity sets the floor at 0.0243.
  • Two-Tower + ranker reaches 0.0329, level with item-item CF (0.0336), but has the highest catalog coverage at 5.4%. Coverage is under 6% for every approach.

Limits

  • Neural rows are full pipelines and the baselines are single-stage models, so this compares pipeline against single stage, not embedding against embedding. The ranker also uses item popularity as a feature.
  • One temporal split of 49,533 interactions, one run per model, and no confidence intervals, so third-decimal differences are not a ranking.
  • The two-tower uses no content features, so it generalizes to unseen users and items no better than ALS.
